    How it works

    Four stages, in this order

    Each stage hands the next one a verified value. A stage that fails stops and flags — it does not invent a value to keep the chain moving.

    Stage 01

    Collection

    A dedicated agent per portal, separating navigation from extraction — so a redesign breaks only one half. The agent stays locked until its structure has been verified against the live site.

    Playwright · staged backoff · structure verification

    Stage 02

    Extraction

    A language model reads the document and extracts eligibility conditions, scoring criteria, specification and award basis — along the PEGS framework. The output is enforced against a schema before it touches the data.

    Claude · PEGS · schema enforcement

    Stage 03

    Matching

    Hybrid search: semantic matching catches synonymous terminology, and exact keyword matching catches standards and part numbers that semantic similarity blurs.

    pgvector · cosine similarity + keywords

    Stage 04

    Alerting

    A tender that clears the profile's match threshold generates an alert in the same operation that stores it — there is no window in which a tender exists and nobody knows about it.

    a trigger in the data layer

    Trust in the data

    A system that decides for you is a system you cannot check

    In a tender submission, one wrong field costs disqualification. Three rules the system is built around:

    Every field, beside its source

    Every tender carries a link to the original notice, always visible. A tender that cannot be verified against its source is not stored — better to omit a record than to show an invented address.

    "Not stated" beats a guess

    The model is instructed to return an empty value when the document does not say. Output that fails validation is sent back for correction once, then goes to a human. Unvalidated output is never stored.

    Isolation between organisations

    Defence companies compete with each other. Each organisation's search profiles, bid statuses and notes are isolated at the database level — not at the application code level.

      Frequently asked

      What we get asked, and what is worth asking

      Where do the tenders come from?

      From public portals, through a dedicated agent per source. Every source is checked before it is connected: if the site's rules forbid automated collection, we do not connect it, and we seek a proper access arrangement with the operator instead. The Israeli MoD tender-list agent is connected today.

      How do you guarantee the data is correct?

      We do not guarantee it — we make it checkable. Every field is shown beside a link to the original notice, and every extraction is enforced against a schema before it is stored. Anything that fails validation is flagged for human review rather than stored as fact. The decision whether to bid stays with you.

      Will our competitors see what we searched for?

      No. Search profiles, bid statuses and notes are isolated at the database level, not at the application code level — so even a bug in the application exposes nothing between organisations. That is a design premise, not an addition.

      What about tenders whose documents are closed?

      Some portals publish only a title, a deadline and a reference number — the specification itself sits behind supplier registration. In those cases we show exactly what is public, and mark the extraction as partial. We will not present a thin record as if it were complete.

      When will there be international coverage?

      After depth in the Israeli market is complete. Many international databases publish open, official data, so connecting to them is technically simpler — but the value to an Israeli user starts with the local sources. Leave your details and we will update you.
